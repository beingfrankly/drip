## What drip is

`drip` is a Rust CLI that fetches hot/trending Reddit posts and RSS/Atom feed entries from sources you choose (Reddit via its own public, unauthenticated RSS/Atom feeds, not scraping and not the OAuth JSON API), normalizes both into a shared `Item` type, keyword-classifies each item into a two-level tree of topics, writes them as one markdown "digest" note per fetch run into your Obsidian vault, and appends a reference bullet to that day's daily journal note. See `README.md` for install steps and the full command reference (`drip init`, `drip fetch`, `drip source`, `drip topic`, `drip config`) — this file doesn't repeat that, only what a coding agent needs to orient itself in the source.

## How drip is used

The core loop, once installed (`cargo install --path .`):

1. `drip init` — interactive first-run wizard. Vault path goes to `config.toml`. Everything else (folders, date format, defaults) seeds the SQLite `settings` table. Also optionally sets up a daily cron entry for unattended fetches.
2. `drip topic add --name <name> [--parent <main>]` / `rename --name <old> --to <new>` / `reparent --name <sub> --parent <new-main>` / `remove --name <name>` / `list` / `test --title <title>` — manage a **two-level tree** of topics (migration `0006_topic_tree.sql`, epic drip-ho5/drip-98u). `--parent` makes the new topic a sub-topic under an already-existing main topic; naming a sub-topic as `--parent` (depth > 2) is rejected in application code, since SQLite can't declaratively express that constraint. `rename`/`reparent` are future-notes-only (they update the DB but never rewrite an already-written digest note; they warn if today's note already has a section under the old name/parent). `remove` refuses while the topic has any descendant — a main topic while it still has sub-topics, a sub-topic while it still has source links — pointing at the command to clear it first. `test --title <title>` is an offline, no-network explain surface: classifies a synthetic title-only item against every saved source's links and prints which fired and where it would route.
3. `drip source add --kind rss|youtube|reddit --url <url> --name <label> --topic <sub-topic> [--exclude <term>,...]` / `link --name <label> --topic <sub-topic> [--match <term>,...] [--exclude <term>,...] [--match-body]` / `unlink --name <label> --topic <sub-topic>` / `list` / `remove --name <label>` — register/manage sources and their links into leaf sub-topics. A source no longer belongs to exactly one topic (that model, and `drip source move`, were removed at drip-ho5/drip-98u): `source add --topic` creates exactly one **ruleless** (accept-everything) link into an already-existing leaf sub-topic — it errors rather than auto-creating one, and rejects naming a main topic directly. `source link` declaratively (re)configures a link's keyword rules — `--match`/`--exclude` **replace** that link's entire include/exclude term lists wholesale, so re-running the same command is idempotent; `source link` can also create a source's second (third, ...) link into a further sub-topic, since links are many-to-many. `--exclude` on `source add` sets **source-level**, title-only exclude terms, a pre-filter that runs before any of the source's links are consulted at all. YouTube channels are fetched via their own Atom feed (`src/youtube.rs` resolves a bare `UC...` channel id, a `/channel/UC.../` URL, or an `@handle` / `youtube.com/@handle` URL to that feed URL — the first two purely, the handle via a single lookup at `source add` time, bd issue drip-ho5.11); Reddit subreddits are fetched via Reddit's own public RSS/Atom feed (`src/reddit_feed.rs` builds that feed's URL, optionally with a sort/time window/search term baked in at registration time) — neither needs any API key, app registration, or OAuth. Fetching for both is delegated entirely to the same RSS client.
4. `drip fetch --source <label>` — fetches one or more saved sources (comma-separated or repeated flag) and/or one or more saved topics via `--topic <name>` (same repeatable/comma-separated form; merged with `--source`, a source named by both fetched once) and/or every saved source (`--all`) into one combined digest note, appends the journal reference. Naming a **main** topic via `--topic` expands to every leaf sub-topic beneath it (a main topic owns no source links directly). Each fetched source's items are keyword-classified per its `topic_links`/`link_rules` rows (`src/classify.rs`) into `(main topic, sub-topic)` sections, so the digest note is always topic-grouped: an H2 `## <main topic>` per distinct main topic referenced, an H3 `### <sub-topic>` under it per sub-topic with at least one routed item, each item a title-only checkbox task line — see `src/digest.rs`'s row below. The note is one-per-calendar-day: a second same-day fetch **appends/merges** genuinely-new items into that day's existing note (preserving ticked checkboxes/manual edits) rather than overwriting it, and dedup suppresses only items already in an earlier written digest (bd issue drip-47u — see the `src/digest.rs` row and the "'Seen' means 'written to a digest'" convention below). `--dry-run` previews both writes (the merge, if a same-day note exists) without touching disk. `--sort`/`--time`/`-q`/`--query` only affect the digest note's own frontmatter/header labeling — they do not filter or search what gets fetched; that's controlled per-source at `drip source add --kind reddit` time instead. `--tag` adds real Obsidian tags. `-n`/`--limit` caps items **WRITTEN** per source, applied AFTER dedup and classification, not before (`truncate_to_limit` in `src/main.rs`, called from `fetch_one_source` — see the "Per-source pipeline order" convention below). `--all` fetches every saved source (via `sources::list`) into one digest, merged/deduped with any `--source`/`--topic` also given — a stable command for unattended cron runs that doesn't need label enumeration.
5. `drip config show/edit/set` — inspect `config.toml` + settings, edit `config.toml` in `$EDITOR`, or set one SQLite-backed setting key (`posts_folder`, `daily_notes_folder`, `daily_note_format`, `default_sort`, `default_limit`, `default_tags`, and the reddit-fetch pacing knobs `reddit_request_delay_secs`/`reddit_retry_max`/`reddit_retry_base_secs`, bd issue drip-6xz).
6. `drip update [--check] [-y]` — checks GitHub Releases for a tag newer than `env!("CARGO_PKG_VERSION")` and, if found and confirmed, downloads + installs it over the running binary (`src/update.rs`, bd issue drip-01g.6). `--check` stops after reporting; `-y` skips the confirmation prompt. Works on every target `.github/workflows/release.yml` (cargo-dist) builds: Linux x86_64, macOS x86_64 + aarch64, and Windows x86_64 — `update::asset_name_for` maps `(os, arch)` to the matching cargo-dist asset (`.tar.xz` on unix, `.zip` on Windows; note cargo-dist asset names carry no version), `extract_binary` unpacks via `tar -xf` (unix) / PowerShell `Expand-Archive` (Windows), and `install_binary` uses an atomic rename over the running exe on unix and a rename-running-exe-aside dance on Windows (bd issue drip-01g.7). Any other platform gets a clear "no prebuilt binary" error pointing at `cargo install`.

Full flag reference and worked examples: `README.md`.

## Architecture Overview

Two storage layers, split by a bootstrap chicken-and-egg constraint (the DB's own location has to be resolvable before the DB can be opened):

- `config.toml` (`src/config.rs`) — bootstrap-only fields: `vault_path`, optional `db_path` override.
- SQLite (`src/db.rs`, schema in `migrations/0001_init.sql` + `migrations/0002_profiles.sql` + `migrations/0003_source_labels.sql` + `migrations/0004_topics.sql` + `migrations/0005_source_topic.sql` + `migrations/0006_topic_tree.sql`) — sources, settings, fetch history, and a dedup ledger. (`migrations/0002_profiles.sql`'s `profiles`/`profile_sources`/`profile_tags` tables are inert leftover schema from the since-removed `drip profile` feature, bd issue drip-1uk.2 — migrations are additive-only and never dropped after shipping, so they're still there but nothing references them.) `migrations/0004_topics.sql` added `topics`/`topic_sources`; `migrations/0005_source_topic.sql` added `sources.topic_id` and a short-lived one-topic-per-source model. **Both are now themselves inert**, superseded by `migrations/0006_topic_tree.sql` (bd issue drip-ho5.2, epic drip-ho5 "Two-level topics with keyword-rule classification", resolved shape per drip-98u.10):

  - **`topics.parent_id`** (nullable, self-referencing FK, `ON DELETE RESTRICT`) makes `topics` a **two-level tree**: `NULL` means a main topic, non-NULL means a sub-topic of the referenced main. Depth beyond two levels is rejected in application code (`topics::create_sub_topic`/`reparent_topic`, both of which check the target parent's own `parent_id` is `NULL` before accepting it), not the schema — the same "SQLite can't declaratively express this" reasoning already used for `sources.topic_id` at `migrations/0005_source_topic.sql:15-21`. `topics.name` stays globally UNIQUE (retained from `0004_topics.sql`) — this migration adds parentage, not a namespace change.
  - **`topic_links(id, source_id, topic_id, match_body, created_at)`**, `UNIQUE(source_id, topic_id)` — the many-to-many table that replaces `sources.topic_id` as the source-of-truth for topic membership: one row per (source, leaf sub-topic) link, so a single source can route into several sub-topics at once, each with its own `match_body` opt-in (whether that link's rules also search an item's body, not just its title).
  - **`link_rules(id, link_id, role, term)`**, `role IN ('include','exclude')`, `UNIQUE(link_id, role, term)` — flat, SQL-queryable keyword rules attached to a `topic_links` row (chosen over a JSON blob specifically so a single term can be added/removed without a read-modify-write, per drip-98u.2's resolution). A link with zero rows is "ruleless" and matches everything.
  - **`source_excludes(id, source_id, term)`**, `UNIQUE(source_id, term)` — source-level, title-only exclude terms: a pre-filter applied before an item is matched against ANY of that source's `topic_links` rows. Deliberately its own purpose-named table rather than overloading the never-written `source_tags` (`migrations/0001_init.sql:59-63`) or a NULL-`link_id` row in `link_rules`.
  - **The backfill (same migration, same atomic `execute_batch`) nulls `sources.topic_id` on every row** after giving each pre-existing source one ruleless link into a deterministic `<old topic name> (general)` sub-topic under a new main topic of the same name — behaviour-preserving (a ruleless link matches everything, so the first post-upgrade fetch routes identically to before) and required, not merely tidy: `sources.topic_id`'s `ON DELETE RESTRICT` FK would otherwise phantom-block deleting an old main topic forever, since a still-populated `topic_id` keeps pointing at it even after every source has a link elsewhere. `sources.topic_id` itself is never dropped (migrations are additive-only) but is now dead: nothing reads or writes it going forward, same fate as `0004`'s `topic_sources`.

A normalized `Item` type (`src/item.rs`) is what flows through digest rendering and dedup — every source kind (Reddit-via-RSS, genuine RSS/Atom, YouTube) produces `Item` directly via `rss::fetch`, so `dedup.rs`/`digest.rs`/`journal.rs` never special-case one source kind vs. another. `SourceGroup.kind` (`src/digest.rs`) is kept for a future kind-specific rendering hook, but it currently drives no rendering decision — the one it used to (`r/{name}` vs bare `{name}`) was removed at bd issue drip-98u.12; see the `heading_prefix` convention below.

## Conventions & Patterns

- **Explicit params over whole-`Config` params.** `digest.rs`/`journal.rs` take `vault_path`/`posts_folder`/etc. as separate arguments rather than a `&Config`, so they stay unit-testable without a real config file. Follow this for new vault-writing code.
- **`PRAGMA foreign_keys` is per-connection, not persisted by SQLite.** `db::open` sets it immediately after every `Connection::open`. Any new code path that opens its own connection must do the same, or `ON DELETE CASCADE` silently stops working.
- **Migrations are additive and versioned via `PRAGMA user_version`.** Add a new `migrations/000N_*.sql` ending in its own `PRAGMA user_version = N;`, then register it in `db::MIGRATIONS`. Never edit an already-shipped migration file.
- **No credentials of any kind are needed or stored anywhere.** `drip` fetches every source kind (Reddit, RSS, YouTube) via a plain unauthenticated HTTP GET against a public feed URL — there is no API key, OAuth flow, or credential storage in this codebase (there used to be, for Reddit's OAuth `client_credentials` API; it was removed, see bd issue drip-1uk).
- **Dedup is per-source, not global.** A crosspost of the same post into two subreddits counts as two distinct items, per `seen_items`'s `UNIQUE(source_id, external_id)` constraint. `src/dedup.rs`'s `filter_unseen`/`record_seen` only ever look up/write a single `source_id` at a time.
- **"Seen" means "written to a digest", not "fetched" or "classified".** `record_seen` fires only on `handle_fetch`'s real-write path — after `write_digest_note` succeeds — never at fetch time and never on the `--dry-run`/zero-new-items paths. This now also covers the two new ways `src/classify.rs` can decline to route an item (bd issue drip-98u.3): an item **dropped** (matches zero of the requested sub-topics' rules) and an item **excluded** (rejected outright by its source's title-only `source_excludes` pre-filter, before any candidate routing runs) are *both* left out of the routed set `fetch_one_source` passes to `dedup::record_seen` — neither is ever marked seen. So `filter_unseen` suppresses an item only once it has landed in an *earlier* written digest, giving "each item appears in exactly one digest" (bd issue drip-47u), and a dropped/excluded item stays eligible for a *later* run even without a fetch in between: widen a `--match` list or narrow a `--exclude` term today, and yesterday's still-in-the-feed-window noise or near-miss can route and render tomorrow, with no re-fetch required. Don't move `record_seen` earlier (e.g. to fetch time, or before classification) without re-checking this invariant.
- **Per-source pipeline order is fixed: `fetch → filter_unseen → classify → truncate_to_limit`** (`fetch_one_source` in `src/main.rs`). `--limit`/`-n` caps items **WRITTEN**, not fetched — it applies to the classified, dedup-filtered *routed set*, last, not to the raw feed. This was measured, not a style choice (bd issue drip-98u.4): truncating the raw feed first, before classification, can leave **zero** routable items at the shipped default limit (`default_limit = 10`) when a source's noisiest items happen to sort first — moving the cap to run last (after classification) turned that into 6 routed items on the same live data, at zero cost, since the whole feed already arrives in one request regardless. Note `src/classify.rs`'s own source-level exclude pre-filter runs *inside* `classify_items`, i.e. functionally after `filter_unseen` in the code as shipped — this differs from the pipeline order stated in bd issue drip-98u.4's resolution comment (`fetch → exclude → filter_unseen → classify → truncate`), though the two orderings are not known to produce different results, since `filter_unseen` only ever removes items already in `seen_items`, and neither dropped nor excluded items are ever added there. Anyone relying on the exact bd-comment wording for this ordering should re-verify against `src/main.rs` directly.
- **`fetched_count` (digest frontmatter, counts rendered checkbox LINES) and `fetch_runs.post_count`/`fetch_run_sources.item_count` (counts DISTINCT routed items) legitimately disagree, by design.** An item that keyword-matches two sub-topics renders once under each H3 (`src/classify.rs`'s "no precedence" fan-out, bd issue drip-98u.3) — `fetched_count` counts both lines, `post_count` and the journal bullet's "N posts" count it once. Seeing `fetched_count: 4` in a note whose journal bullet says "3 posts" is expected under rule overlap, not a bug — do not "fix" one to match the other.
- **Search-scoped source registration and keyword-rule classification are complementary layers, not alternatives — never collapse the former into the latter.** Measured at full feed depth (`hot/.rss?limit=100`, not just a shallow top-N sample): 88% of a search-scoped source's results were absent from the same subreddit's broadly-fetched `hot` feed even at its maximum reach (bd issue drip-98u.9). Keyword rules can only route what retrieval already fetched — folding a search-scoped source (e.g. `cc-hooks`, a `--search hooks` registration) into one broadly-fetched source and relying on a `--match hook` rule instead would permanently lose that 88%, with no rule able to recover content a broad fetch never retrieved. Register search-scoped sources per the retrieval reach you actually need; use `drip source link --match`/`--exclude` only to refine what a source already retrieves, never as a substitute for scoping the fetch itself.
- **The digest note body has no source headings and no author.** Since bd issue drip-98u.6/drip-98u.12, the body is H2 main topic → H3 sub-topic → a title-only checkbox line per item (`- [ ] **[title](url)**`, plus a leading `⚠️ NSFW ` marker where applicable) — no `### <source>` heading beneath the sub-topic, and no ` — u/author`/` — author` suffix on the line. `SourceKind::heading_prefix` (the old `r/{name}` vs bare `{name}` rendering hook) is gone entirely, not just unused — a source's *label*, not its real subreddit, was what it prefixed, which was actively misleading for a search-scoped label like `cc-hooks` (bd issue drip-98u.12). The **Sources:** summary line and `sources:` frontmatter both render every source's bare label with no prefix now, and are consequently the only place in the body a source's name appears at all.
- **Source identity across kinds is `(kind, name)`, never bare `name`.** `main.rs`'s `handle_fetch` keys its `source_ids` map by `(kind, name)` tuples specifically because two sources of different kinds can legitimately share a label string (e.g. both named "rust") without being the same source — keying by bare name caused a confirmed crash + silent dedup corruption during drip-15n.9.6's review. `--source` lists are also deduplicated (order-preserving) before fetching, since an exact duplicate entry causes a `fetch_run_sources` primary-key collision otherwise.
- **Tests never hit real services or real user state.** RSS calls are mocked with `mockito`; vault/config/DB paths use `tempfile::tempdir()` fixtures. Never point a test at the real `~/.config/drip/` or a real Obsidian vault.
- **`reqwest` uses the `native-tls` feature, not `rustls-tls`.** Confirmed live: Reddit's edge returns a hard `403 Forbidden` to `reqwest`'s `rustls` backend even as the first request in a freshly-reset rate-limit window, while `curl` from the same machine succeeds — looks like TLS-client fingerprinting, not ordinary rate-limiting (`429`). Switching to `native-tls` (the system's real TLS library) resolved it; verified end-to-end against real `r/rust`. This means `drip` now needs system OpenSSL dev headers to build (`libssl-dev`/`pkg-config` on Debian/Ubuntu — see README Prerequisites), unlike `rusqlite`'s `bundled` feature, which needs nothing external. Don't revert to `rustls-tls` without re-confirming this is still needed — Reddit's bot-detection behavior could change.

## Claude Code Skill Maintenance

- **Keep `.claude/skills/drip/SKILL.md` in sync with the real CLI.** Any change touching `src/cli.rs` (new/removed/renamed subcommand or flag, changed default, changed semantics) or adding a new source kind or settings key (`src/types.rs`, `src/settings.rs`) must update `.claude/skills/drip/SKILL.md` in the same change. A skill that's drifted out of sync with the real CLI is worse than no skill at all — an agent will confidently give wrong flag guidance.
